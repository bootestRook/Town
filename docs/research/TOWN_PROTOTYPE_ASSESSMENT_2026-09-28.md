# 小镇经营原型：研究与实施评估

日期：2026-09-28。对象：用户指定的《佣兵小镇》APK、拆包档案、参考截图，以及当前 Godot 基座。

后续状态：用户随后确认 750×1334 竖屏并要求实施地图与建筑阶段，资源复制限制也已移除。本文件保留研究时点的评估；当前完成情况以 [开发清单](../TOWN_PROTOTYPE_LIST.md) 为准。

本轮只完成研究与用户明确提出的 Godot 4.7.1 标识调整。地图、英雄 AI、商业资产导入均未实施。下文的首版范围、行为优先级和技术分工是建议，不是已经完成的功能。

## 1. 结论

可在现有基座上做出真实可玩的同类原型。资料足以确定地图构成与英雄行为链，无须再次全量拆包。

首版的核心应当是“看得见的小镇 + 会因需求行动的英雄 + 实际影响行动的库存、座位与个人钱包”。只让角色随机散步，或到建筑旁播放动画，不足以体现该游戏的经营机制。

优先级建议：地图和寻路 → 一名英雄完成恢复流程 → 多英雄、四种服务与交易 → 一个可见野区形成持续循环。暂缓地下城、复杂技能、抽卡、长线养成、付费和社交系统。

最主要的成本不是背景拼接，而是角色动画适配，以及多人竞争服务时的中断、占位、库存和结算一致性。

## 4. 地图实际上如何拼接

### 4.1 已确认的结构

主预制体是 `03_美术资源/04_预制体/resources/view/map/Map.json`。它仍为 Cocos 编译序列化结构，包含类表、属性掩码、节点数据和引用表，不是可直接拖进 Godot 的场景。本轮按属性掩码读取了节点和地图组件；未声称已完成完整场景转换。

主背景由六块组成：

| 上排 | 上排 | 上排 |
| --- | --- | --- |
| bg1 | bg2 | bg3 |
| bg4（下排） | bg5（下排） | bg6（下排） |

- 每块 2066×2427；合计 6198×4854。
- `nodeBg` 的尺寸和六个子节点的位置、锚点共同支持上述拼法。不能把图块全部按中心锚点直接摆放。
- `bg7`、`bg8` 是额外场景背景，尺寸为 2249×2080，不属于主背景的 3×2 拼图。
- `CptMapBg.js` 通过 `c1_map_bg` 切换背景资源组，主背景与城镇逻辑网格是分开的。
- `CptMapCityElements.js` 分出背后障碍、地面装饰、建筑与角色、上层元素、浮动信息五层。
- 道路也存在独立预制体：`MapBuildAssetsMgr.js` 映射了 `OrnamentRoad001Prefab` 至 `016Prefab`。不能把整张画面当作一张不可编辑的地图截图。

用户截图中的草地区、悬崖、水域属于整体地貌；建筑、废墟、可清理物与英雄需要独立对象。首版应保留这一区分，才能同时支持建筑交互、遮挡和寻路。

### 4.2 逻辑网格与建筑

从 `Map.json` 的城镇组件核实：

| 参数 | 原包值 |
| --- | --- |
| 格子外接尺寸 | 38×19，2:1 菱形 |
| 网格数量 | 113×110 |
| 建筑区域端点 | (26,20) 到 (90,90) |
| 中心／初始聚焦格 | (58,56) |
| 静态排除格 | 7,511；坐标唯一且均在网格范围内 |
| 排除后的候选格 | 4,919，尚未扣除建筑、障碍等动态占地，不能当作可通行总数 |

`CityMapDataMgr.js` 先读取静态排除格，再创建格子数据和 A*；`BaseBuildingInfo.js` 登记建筑占地、计算门口格并更新遮挡排序。

`c33_jianzhu` 共 18 条建筑定义，包含占格宽高、两个门口方向、初始格位置、美术引用及重建门槛。抽查医院、餐馆、旅馆、酒馆均为 8×8 逻辑格，这些格子不是 8×8 像素。

因此，移植的重点应是四套坐标的一致：逻辑格 → 世界像素 → 贴图锚点 → 建筑入口。Cocos 的 Y 轴方向与 Godot 2D 不同，必须统一转换后再验证；不能只把 Y 值取负便假定所有锚点和层级都正确。

### 4.3 Godot 实现建议

- 大背景块和固定地貌使用场景中的独立图像节点；独立建筑、角色和遮挡物按落脚点排序。无需为了网格寻路把整张美术切成普通 TileMap 小格。
- 逻辑层维护可用格、障碍占地、建筑入口、排队点和跨区入口；使用原生 `AStarGrid2D` 的格子路径能力。其继承 `RefCounted`，可封装在 Feature 的领域导航服务中，不需要领域层访问 Node。
- 本机 4.7.1 API 已核实 `AStarGrid2D.get_id_path` 和 `CanvasItem.y_sort_enabled`。具体格子形状、斜向移动策略与其它参数在实施前逐项查签名及测试，不在本轮假定。
- 渲染从领域位置插值；移动完成由模拟状态确认。动画结束事件不能决定到达、扣费或恢复结果。
- 建筑开始先固定布局。后续新增移动建筑时，先验证门口与野区仍连通，再原子提交新位置与导航版本；失败则拒绝本次布局操作。
- 场景固定骨架保存在 `.tscn`；动态英雄、排队标记和状态气泡才由代码实例化。

六块主背景若全部按未压缩 RGBA8 同时驻留，像素数据约 114.8 MiB，未计 mipmap、角色图集和其它缓冲。这是容量估算，不是当前显存实测。首版只加载需要的区域与一组外观；图片压缩、边缘接缝、滤波和缩放要一起验收。

## 5. 英雄 AI：已确认与建议范围

### 5.1 原包事实

`04_配置表/JSON原表/resources/common/btree/` 下有 22 份 JSON。默认树 `hero_auto_btree` 有 1,753 个树节点、777 个叶节点，包含大量展开重复分支；这不是 777 种行为，也不意味着原型需要建立同等规模的通用行为树编辑器。

抽查执行模块后确认以下流程：

| 行为 | 已确认依据 | 首版处理建议 |
| --- | --- | --- |
| 野外活动与返城 | 默认树、`Hero.checkNeedBackCity` | 一个野区，明确返城原因与目标 |
| 出城／过桥 | `OutCityBehavior`、`GetByBridgeBehavior` | 实际通过入口移动，不以随机传送替代 |
| 匹配交易订单 | `Hero.checkIsNeedExchange`、`HeroExchangeBehavior` | 只卖订单需要的材料，转移真实物品和双方金币 |
| 医疗、饮食、休息、娱乐 | `Hero.checkIsNeedRecover`、`buyDrugAndRecover` | 四种需求驱动四类服务 |
| 到店与排队 | `HeroLineUpAwaitBehavior` | 有具体排队点，满员等待可以恢复运行 |
| 预留座位 | `ReserveSeatBehavior` / `BuildModel.heroReserveSeat` | 座位有唯一持有者，中断必须释放 |
| 缺货、无钱、店铺未开／升级 | 默认树中的对应节点 | 进入有原因的等待状态，相关条件改变后重新评估 |
| 死亡与复活 | 独立复活树，生命不大于零 | 灵魂返回复活点、计时完成后恢复行动 |
| 手动任务覆盖 | `HeroBtreeModel.onRevOrder` / `priorityRunTree` | 首版仅返城／派遣；其它专项玩法后置 |

城内需求阈值在本包中为生命 70%、饱食 50%、疲劳相关属性 40%、心情 40%。这些是“需要服务”的检查，不是统一的野外返城阈值；而且建筑是否存在会影响部分分支。

`checkNeedBackCity` 明确检查疲劳相关属性耗尽、饱食耗尽与净化之力；生命变化和专项战斗还有其它路径。本轮不把所有返城条件压成一个百分比。

原包调度器还有放逐、转生、训练、地下城、首领、装备等任务的中断和恢复顺序；首版没有必要连同这些系统一并实现。

### 5.2 推荐的首版 AI 结构

采用“目标决策 + 可中断动作状态机”，暂不增加通用行为树 DSL 或编辑器。目标从需求和玩家指令产生，动作负责到达和资源占用。

建议优先级是本项目设计，不声称与原树逐节点相同：

1. 死亡／复活与危险返城。
2. 当前已经提交的短事务，以及已经开始的服务；避免每次需求波动都取消重来。
3. 可执行的玩家召回／派遣命令。
4. 危急恢复；交易能解决缺钱时，先做可达且可支付的材料出售。
5. 已匹配订单、普通生活需求。
6. 条件满足则冒险；暂时没有任务时短暂闲逛。

动作状态至少包含：决策、前往目标、等待服务、预留座位、进入建筑、消费与恢复、离开建筑、交易、出城、战斗、返城、死亡和复活。相同服务使用同一流程，由服务类型、恢复属性和配置驱动，不按医院等具体 ID 在共享代码里分支。

固定步长推进模拟，先建议 10 Hz 决策／经营 tick；表现按渲染帧插值。战斗结算继续使用明确的模拟时序。上述频率为待测起点，不是已验证的性能指标。

必须处理的异常：目标消失、通路改变、最后一份库存被其它英雄买走、最后一个座位被占用、金币不足、订单撤销、移动中召回、服务中退出、暂停后恢复。等待不应每帧反复寻路；记录导航／库存／订单版本，有条件变化或重试时间到达时再决策。

每名英雄要能显示简短中文意图，例如“去吃饭”“医院排队”“缺少绷带”“金币不足”。调试信息放在可关闭的检查面板中：当前目标、行为原因、目标建筑、路径、占位和上一次失败原因。

## 6. 经营规则必须随 AI 一起落地

官方玩法说明与本地代码都区分镇长账户和英雄账户。原型也需要保持这一点：

```text
英雄冒险 → 英雄材料和金币增加
    ↓
交易所按订单收购 → 镇长付钱，英雄交材料
    ↓
镇长生产恢复品 → 库存实际增加
    ↓
英雄进店消费 → 英雄付钱，库存减少，服务完成后恢复
    ↓
英雄再次冒险
```

如果地图和 AI 独立于库存、订单、钱和服务容量，经营决策就不会改变英雄行为。推荐首版即保留最小的采购、生产和服务结算。

付款、扣库存与服务凭据要一次提交；取消／重试不允许重复扣款。排队不是已经购买，预留座位也不等于已经完成服务。原包部分结果来自服务器；离线原型必须自行定义本地权威规则，而不是模拟原运营接口。

要专门验证经济停滞：英雄无钱买恢复品、镇长无钱收材料、全城缺少生产材料时，系统应该明确显示原因，并允许玩家通过采购／补货／价格等已定义操作恢复。不能仅靠正常初始资金掩盖这类问题。

## 7. 美术适配评估

### 7.1 地图与建筑

已直接查看档案中的地图和建筑分类预览，风格与截图吻合：粗描边、低饱和地面、颜色鲜明的建筑屋顶、斜角建筑、较小的角色比例。

完整贴图与透明切图不能简单相加计算独立资源数。切图索引带有原尺寸、裁切偏移和旋转标记，移植时要检查这些信息；不能仅依 PNG 宽高推断原节点的落脚位置。

美术可用性验证首先选择一个地貌接缝、一座高建筑和一名角色，检查缩放、透明边缘、穿行遮挡和门口对齐，再扩大资源量。

### 7.2 角色动画是主要技术风险

档案索引有 265 组 Spine，全部标记 3.8.99，其中 238 组 JSON、27 组 SKEL；它们含不同朝向、怪物、NPC 和特效，不是 265 名英雄。

本轮抽查的角色具有正面／背面资源和 `idl`、`move`、`atk`、`skill` 等动作。`RoleSpineHelper.js` 负责正背切换与水平翻转。原资源不等于一套完整八方向逐帧动画。

[Spine 官方版本说明](https://esotericsoftware.com/spine-versioning)要求导出数据与运行时的主、次版本匹配。因此不能假设当前 spine-godot 可直接读取这份 3.8 数据，也不能只改 JSON 中的版本字符串。[官方 Godot 运行时说明](https://esotericsoftware.com/spine-godot)还要求选择对应 Godot 的扩展，导入时需注意预乘 Alpha 限制。

| 方案 | 适用情况 | 代价与验证 |
| --- | --- | --- |
| 离线烘焙为透明动画图集，Godot 使用序列帧 | 首版以行走、战斗、生活行为为主，不需要骨骼换装 | 建立一次可重复的转换流程；先验证一个正背角色的待机、移动、攻击及透明边缘；帧数、尺寸影响内存 |
| 接入匹配的 Spine 运行时 | 明确需要骨骼混合、换装和插槽特效 | 3.8 数据适配、4.7.1 扩展构建、导出平台、许可证及维护都要验证，并先写 ADR |
| 制作原创序列帧角色 | 按当前项目商业资源隔离规则推进 | 新美术制作成本更高，但可直接沿原生图集管线持续使用 |

技术上建议首版优先采用序列帧这条稳定交付路径；它可以作为长期方案，不预设以后一定重写为骨骼运行时。本轮尚未进行烘焙试验，也未安装第三方运行时。[Spine 运行时许可](https://en.esotericsoftware.com/spine-runtimes-license)需要在实际选择集成路线时核对，不能由文件可读取推定可分发。

### 7.3 当前项目规则与“参考资源”的边界

`AGENTS.md` 明文要求“不得复制商业源码、名称、数据或资产”。当前请求是先研究评估，且使用“参考”，因此本轮只读分析拆包资料、保存研究摘要，没有把商业代码、配置或美术复制进运行时目录。

后续若要求直接使用这批原包美术，需要明确它与该规则的适用边界及可用范围；如果沿用现有规则，就根据本次结构研究制作原创资源和小规模自有配置。无论选择哪条资产路线，英雄逻辑都建议按本项目契约重新实现，不搬运 Cocos 客户端。

## 8. 模块与实施顺序建议

首版新增一个 `town` Feature，领域内分模块，不急于拆成相互依赖的多个 Feature：

| 模块 | 状态与职责 |
| --- | --- |
| TownState / TownFeature | 唯一状态所有者；英雄、建筑、订单、双方账户；命令、快照和事件 |

## 9. 验证清单与风险排序

| 优先级 | 风险 | 验证方式 |
| --- | --- | --- |
| 高 | 动画版本／透明边缘／朝向 | 单角色正背待机、走路、攻击实际播放；再确定批量管线 |
| 高 | 预约、库存与钱不同步 | 两名英雄抢一个座位／最后一份商品；取消、重复请求后检查账本与预约 |
| 高 | 地图看起来连通但入口不可达 | 每栋功能建筑到城门连通检查；遮挡、窄口和封路测试 |
| 高 | 经济或 AI 永久停滞 | 缺货、无钱、目标撤销、全店满员；改变条件后自动恢复，或明确等待玩家行动 |
| 中 | Cocos 坐标、锚点和排序迁移 | 对照参考图检查道路、脚底、门口与高建筑遮挡 |
| 中 | 背景和帧图集内存 | 记录实际纹理内存、帧耗时；按目标设备做 6／15 英雄测试 |
| 中 | 更新频率改变规则结果 | 相同 seed 与意图序列在不同表现帧率下得到相同领域结果 |

每阶段保留可运行产品。M3 完成标准建议为：在常规供给场景中连续运行 10 分钟，多名英雄完成至少三轮完整循环；非法目标、缺货、满员、无钱、死亡、中断各有可复现案例；暂停与重开后没有座位泄漏或重复支付。最终继续运行现有 `project.py check`，并做可见画面验收，不能用 headless 检查代替美术与行为观看。
