# ADR 0010：英雄管理三页与地图、远征队伍分离

日期：2026-09-29。状态：接受，已实施。

## 背景

用户要求英雄信息页的「更换英雄」进入完整的上阵、培养、图鉴三页，并提供四张新参考。改动前 `main.team` 同时服务地图活动与独立挑战，无法同时表达源公寓容量和固定五人远征；继续共用会把地图上阵限制误当远征规则。源依据为 `HeroStandbyGoBattlePageCtrl`、`HeroStandbyUpStarPageCtrl`、`RecruitIllustrationListPageCtrl` 和 `CptHeroInfoItem`，本机检索入口见 本机来源索引（未随包提供；[资源来源登记](../../THIRD_PARTY.md)）。

## 决策

保留 `main.team` 的地图活动英雄语义，既有 `hero_team` 命令只操作地图队伍；新增 `main.expedition_team` 表达独立五人远征队，新增 `expedition_team` 命令供原地下城队伍弹窗使用；守卫和海底遗迹也读取独立远征名单。地图与独立挑战分别读取自己的名单，不保留根据上下文猜测名单的兼容路径。初始出战选择仍为原三英雄，不因容量提高自动增加出战或拥有英雄，也不清空已有48人拥有名单。

新增 `main.camp_level`，本地演示初值采用5级，与本项目既有主城及生活店5级演示初值一致。地图上阵容量从源 `c58_gongyu` 按等级查 `num`；已核实5级为7，禁止在UI硬编码7或照抄参考人数。这是本地演示初值，不是原游戏新账号初始营地等级；地图常驻人数、地图上阵容量与远征五人上限分别表达。

地图上阵的单人切换、过滤后快捷选择均经领域命令提交：先校验拥有身份、地图动作/实体可用性、容量及远征中成员限制，再一次性提交名单；下阵后允许立即通过单卡或快捷操作重上，不记录更换冷却。快捷操作依据同一权威快照，保留进行中远征里不可撤下的现有成员，再按当前元素候选的战力降序、同战力ID顺序补至容量，统一提交；无候选或无效元素拒绝而不清空原队伍。过滤本身只改变候选呈现，不直接改状态。未烘焙地图动作的招募待命英雄仍可查看和培养，不能伪装成可上阵地图角色。已有真实返城、待命、服务和复活规则继续由地图领域负责。

培养页面按新参考呈现8个入口，当前仅升星可操作，其余按参考锁定；遮挡文字不得推测补全。此页锁态不撤销英雄信息页已经可用的宠物、神器入口。当前APK的培养控制器只提供英雄、宠物、神器3类结构，与新参考8入口不一致，不把锁定外观写成对应子系统已经实现。

图鉴按源 `tujian.show_id` 读取最高阶静态定义供展示，不升级、替换或创建拥有实例。四分类按新参考呈现：「全部」显示已导入定义；「卡池」读取当前招募等级可抽取品质与正 `weight`；「特殊卡池」「活动」因当前版本缺少直接成员配置而保留空列表，不按名字、外观、品质或猜测归类。源APK控制器本身仅有全列表，不能声称源四分类机制已完整移植。

全部规则与状态归属 `town` Feature，沿用当前静态Definition、可变State、Intent/Command、CSV/schema和资源管线。固定页面结构写入 `.tscn`，表现层只读取快照和提交意图；不新增跨Feature依赖、第三方依赖、Autoload、全局事件总线、存档文件格式或迁移。图鉴静态展示对象不能通过养成入口写回拥有状态。

## 实施与验收

领域实现为 `TownHeroDeployment`，固定界面为 `main_hero_management`、`main_hero_library_card`、`main_hero_training_row` 的 `.gd`/`.tscn`。新导入17张源UI图、74条图鉴展示记录与13级营地容量；源和现有资源管线不变。更换英雄按源入口关闭原详情，管理页返回原抽屉或招募入口；培养卡打开详情再返回时恢复培养tab及滚动。当前详情英雄处于远征中时，入口先拒绝跳转。

`tests/test_hero_management.gd` 覆盖队伍分离、源容量、原子拒绝、即时重上及快捷补回、远征成员保留、真实升星、图鉴只读及未烘焙英雄拒绝地图上阵。三份原生回归日志均通过，覆盖三页、三尺寸及既有英雄信息/抽屉；最终管理页回归另验证三页模拟触摸拖动不误上阵、不误开技能，卡片和培养操作按钮将拖动传给滚动容器；首轮完整检查的Godot阶段5812条断言通过，但发布清单因视觉微修过期而失败，不能记作完整检查通过。
